# 新版雪球菜单：可复用自动部署流程

适用 Proloader 已支持登录且有 OP/命令方块权限的网易手机版租赁服。不是 Java、任意插件服或其他版本的通用安装器。
此流程供助手通过 Proloader MCP 自动执行，也可以通过对应 `proloader ai` CLI 操作。不需要用户手摆命令方块。

## 固定来源

只用 `templates/snow_menu_v3/program.json`：用户最后给的38条前置＋三改动画UI，从已部署版本整理，服务器编号须在部署时提供。
58块（主链56、计时链2），六项功能、60秒互传、第9快捷格锁定16个雪球；不含起床战争、金币或旧菜单UI。
此槽位原物品会被持续替换，沿用用户原指令。循环头后接无条件连锁，箭头按蛇形连接，计时循环延迟20刻。
模板相对位置包含计时链在Z+10的实际布局，部署时以JSON为准。

## 每次部署输入

- 服务器编号、密码（仅传进程标准输入，不写入包、命令历史、日志或报告）。
- 主世界主城XYZ。
- 指令区XYZ，默认12000 280 12000；必须是确认可用的远处空位。

缺少主城或目标服务器时先询问，不能沿用其他服坐标。同一服务器只部署一套此菜单；菜单、互传、dh、dh1、plsm_state和常加载名共用，不能并行放第二套。

## 1. 离线生成

从项目根目录运行（下面是占位示例，替换编号和坐标）：

```sh
python3 -m tools.package_snow_menu --server 服务器编号 --home -68 118 246 --origin 12000 280 12000 --output cache/本次雪球菜单
python3 -m proloader ai lint cache/本次雪球菜单/snow-menu.ai.json
```

生成源JSON、保留类型/朝向/延迟的mcstructure，以及安装清单install.json。输出目录必须为新目录，避免覆盖旧部署记录。
mcstructure只含命令方块；平台、规则、积分项和常加载由下面流程建立，不能仅导入结构就宣称安装完成。

## 2. 登录与预检

1. 查询MCP spec、status。已有连接先查启动记录确认服务器身份；status只有在线状态和名称，不能据此证明服务器编号。禁止同身份并连。
2. 需要新连接时由助手启动 `python3 -m proloader ai serve --server 编号 --password-stdin`，复用身份锁。没有本次部署授权时不连接；本流程文件的生成本身不授权进服。
3. `testfor @s`确认权限；未确认时等待用户OP授权，不先建平台。确认假人位于主世界；无法确认维度时先解决，不在其他维度执行规则/建造。
4. 查 `scoreboard objectives list`、`tickingarea list`和既有部署记录。同名目标已存在须确认是本菜单的兼容旧部署，不能删除其他玩法积分项或强加载。已有菜单升级见下文。
5. 先传送至指令区，并用位置探针确认已抵达。检查平台范围和指令链周围没有建筑/红石；不自动清空地形。目标不空则换位置并重新生成。

## 3. 自动建区、写入、验证、启用

1. 逐条执行install.json的setup。只对缺失积分项执行add；存在时保留内容，不能把负回执笼统视为“已存在”。
2. 逐条执行prepare：先将总开关置0、排除假人、关闭两类反馈、启用命令方块，再建立强加载。若常加载名已存在，核对范围；名额不足停止，不能删其他区域。
3. 调用MCP program deploy，传snow-menu.ai.json。deploy先检查所有目标为空气，再放外壳、暂存NBT并逐块读回；此时不会自行启用。
4. 执行platform，以keep方式在链下补平滑石平台，不清除/覆盖既有方块。testforblock核对平台，`tickingarea list`核对加载范围，查询三条gamerule核对规则。不能只看发送回执。
5. program verify（active=false）须逐块通过；失败先inspect，保留已完成部分，不盲重放deploy。
6. program arm，先连锁尾后循环头；program verify（active=true）须全部通过。然后执行start打开总开关。
7. 读回循环头与链尾NBT，确认类型、朝向、auto、delay、Command一致；等待游戏刻后单独检查动画/计时推进。真人投雪球、抬头确认、低头取消、双人互传属于效果验收，未测试就如实记录。
8. 记录服务器编号、坐标、模板哈希、58块核对结果、规则/常加载结果、玩法待验收项，不保存密码。完成后按用户要求退出假人；常加载使菜单不依赖假人在线。

所有RPC须同时检查ok及confirmed/all_confirmed；超时或负回执可能已写入，先inspect/查询再决定，不换request_id盲重试。失败保持总开关0，能安全确认身份时关闭开关；不得声称事务回滚或继续启用。

## 已有菜单更新与以后新给的指令

同一布局更新：先总开关0，备份旧源和新鲜NBT，program disarm，再program write、verify、arm、verify --active，最后开总开关。
类型/朝向/数量变化：不能直接write；先生成迁移计划，明确旧块和新块差异，只处理本菜单方块，不清空整个指令区。

用户以后给新原文时：保存原文和哈希，先解释循环/连锁连接、条件模式和延迟，再整理成proloader-ai-v1模板。用layout布线；校验每个箭头通向下一块，跨链独立处理。
不能把任意粘贴文本直接当作现成模板，也不能自动混入旧版。回城命令、setup/start/stop和总开关约定改变时同时更新打包器并离线验证。

以后可以直接对助手说：**“按新版雪球菜单流程部署到服务器……，主城……，指令区……”**，助手读取本文件按步骤自动完成。
